# 推荐流动态采集与对照

## 目标与边界

确认首页展示、点击、真实观看和返回刷新分别触发哪些请求，参数来自什么状态，
以及 NeoBili 与官方客户端的差异。第一轮采集网络行为，不把接口成功等同于推荐生效。
静态依据见 [客户端协议](CLIENT_NETWORK_PROTOCOLS.md) 与
[实现契约](CLIENT_API_IMPLEMENTATION_CONTRACT.md)；操作原则见
[开发与测试](DEVELOPMENT.md#官方推荐请求对比)。

由操作者通过 Device Hub 控制用户已授权的真机。官方中国版、国际版、NeoBili、
第三方处理的解密包分别标记，不能混为同一版本。首轮优先使用手机已安装的官方 App。
解密包用于解释不明字段；本轮不需要安装它或修改官方 App。

## 采集准备

1. 在 Device Hub 选择真机，确认连接、解锁、画面可见且点击有效；不选择 Simulator。
2. 记录机型、系统、App 名称、版本、build、网络类型、登录状态和首页相关设置。
   账号与设备身份只记录脱敏代号，不在文档写原值。
3. 检查 Mac 的采集服务、当前地址和手机路由。使用已有可信抓包配置；
   Wi-Fi 手动代理与 WireGuard 不叠加。连接方式、证书及权限变化由实际界面确认。
4. 先进行一次连接试采：打开首页并下拉一次，确认可以读取推荐响应，而非仅收到广告、
   日志或加密连接。验证能匹配手机上至少两张卡片的标题和顺序。
5. 校准 Mac 时间与手机操作时间。为每批独立保存流量文件和操作时间线；记录点击前后
   画面、请求起止、响应到达和卡片显示时刻。不靠 `flush` 或时间猜测用户动作。
6. 原始流量、截图和日志存于仓库外的私有采集目录，限制读取权限；文档只保存
   脱敏字段、结构、证据引用及分析。忽略的验证目录可放脱敏结果。

采集通道验证前不启动正式观看实验。启动、切换代理和检查页的流量单独标记。

## 第一轮：首页到观看再返回

每批先做官方，再做 NeoBili；两者使用用户自己的同一账号。保留既有登录与设备状态。
共享账号意味着先做的操作可能影响后做的结果，本轮优先对比请求链路，不能据此单独判断因果。

| 批次 | 手机操作 | 记录重点 |
| --- | --- | --- |
| A 启动与刷新 | 从后台关闭目标 App，重新打开，停留首页 15 秒；下拉一次，待响应及卡片稳定；再下拉一次 | 首次/后续状态、游标、会话、公共参数、返回卡片及顺序 |
| B 展示与翻页 | 首页静止 10 秒；向下滚动约一屏，静止 10 秒；滑回原卡片，静止 10 秒；继续滚到触发一次翻页 | 可见卡片、展示与时长事件、重复展示、分页请求与追踪字段 |
| C 点击不观看对照 | 选普通视频卡片，记录标题、视频 ID、位置和服务端追踪字段；点入后尽快暂停，5 秒后返回；不刷新等待 15 秒 | 点击上报、进入来源、自动播放产生的实际进度、退出/停播事件；不能称为零观看 |
| D 实际观看 | 从首页选普通视频，记录相同信息；点入、确认真实播放，连续观看至少 120 秒，不拖动、不点赞、不收藏；返回首页，等待 15 秒，再下拉一次 | 起播、观看心跳、播放位置与累计时间、播放 session、退出和刷新上下文 |
| E 离开与返回 | 停留首页，切到后台 15 秒，再回前台；等待 10 秒，下拉一次 | 前后台事件、会话是否延续、参数缓存及新的请求 |

卡片不足两分钟时换长视频；缓冲、暂停或广告占用不算实际观看时间。
等待分段执行并持续检查采集，避免一次长等待掩盖断线。播放中仅查询状态，不额外点按。
手机页面发生非预期变化时记录偏差，暂停本批，不能事后补成预定操作。

## 后续按需开展的批次

首轮整理后再选择能解决明确缺口的操作，不同时改变多项条件。

| 批次 | 操作 | 要确认的问题 |
| --- | --- | --- |
| 来源对照 | 同一视频分别从首页、搜索、历史进入，播放并返回 | 点击来源、追踪标记和观看上报如何关联 |
| 播放状态 | 分别暂停/继续、拖动、结束和切换下一视频 | 累计观看与播放位置、事件时机及 session 更新 |
| 兴趣反馈 | 在单独批次点赞、取消点赞、收藏、取消收藏 | 实际业务请求、成功响应与附带的推荐反馈 |
| 设置映射 | 每次只改自动播放、静音或布局中的一项，按提示重启，再采首页，最后恢复 | 设置与请求参数的真实映射，不把短期不变认作协议常量 |
| 兴趣效果 | 先记录若干次首页，再真实观看多条同类长视频，最后重复记录首页；另做重复轮次 | 主题占比和兴趣响应速度；共享账号、候选供给、随机性及时间带来的干扰 |

退出登录、踢设备、清理数据与重装会改变实验基线，本轮不执行。
如后续专门验证账号重置或退出清理，单独记录与用户协调。

## 每批分析与交付

1. 输出实际操作时间线，包含客户端版本、卡片身份与操作偏差。
2. 按时间列出推荐、点击、曝光、观看及相关请求的地址、方法、编码、参数来源、响应状态。
   标记重试、批量延迟发送、缓存、预加载和仍不可读的连接。
3. 对照静态预期，区分“确认出现”“当前场景没观察到”“无法读取”。
   不把没请求直接解释为本地计算，也不把一条请求的成功推广到所有上报。
4. 对齐两客户端的真实动作逐项比较：字段是否缺失、值的生成、触发顺序、延迟和视频关联。
   原始凭据、Cookie、token、ticket、设备编号和未知敏感值不得输出或提交。
5. 必要时回查解密包的对应实现；8.89 静态样本与其它版本的运行结果保留版本边界。
   仅凭抓包不能给出函数调用栈；需要内部运行时跟踪时另行确认环境。

## 中断与收尾

- Device Hub 不可控制、手机锁屏、路由不通或推荐响应不可读：停止正式批次，先定位通道问题。
- 视频持续缓冲、采集断流或页面操作失败：标记该批不完整，修复后重新采集。
- 系统权限、证书或安全提示无法由已有授权直接处理时，由用户完成必要步骤。
- 完成后正常停止采集并确认文件写完，断开实验隧道，恢复本轮改变的网络及 App 设置，
  验证 App 正常联网。保留原账号和应用数据。

只报告本次实际完成的批次和证据，不以操作计划替代采集结果。

## 已采集的官方国际版观测

当前样本为官方国际版 `build=91300300`、`mobi_app=iphone_i`、`platform=ios`，
用户在真机完成 A～E 操作。原始材料位于仓库外私有采集目录，脱敏分析为
`/Users/elsterlee/Documents/NeoBiliCapture/current/official_analysis.json`。
以下是这批样本的观测，不自动推广到中国版或其它版本，也不直接作为硬编码依据。

| 操作 | 可读记录 |
| --- | --- |
| A 启动与两次下拉 | 三次推荐响应均 HTTP 200、业务 code 0，卡片数 9、9、10。首次 `flush=0/pull=1/open_event=cold/login_event=2`；后两次 `flush=6/pull=1/open_event=""/login_event=0` |
| B 滚动与返回 | 两次分页均 `flush=8/pull=0`，各返回 9 张卡片。通过 `param` 匹配“导播带头开串”卡片，找到两条 `tm.recommend.feed-card.duration.show`。仅共享 `track_id` 不足以识别单张卡片 |
| C 短停留 | 匹配 GTA6 卡片的一条 `tm.recommend.main-card.0.click`。对应历史请求 `progress=1/duration=29`、业务 code 0；另有其它视频的历史请求，不归给本次点击 |
| D 观看后刷新 | 同一“导播带头开串”视频有两条点击及两条成功历史请求：`progress=18`、`151`，两者 `duration=241`，`start_ts` 不同。用户确认先有误操作暂停，随后再次进入。返回刷新 `flush=6/pull=1`，成功返回 9 张卡片 |
| E 后台返回并刷新 | 一条推荐请求 `open_event=hot/flush=6/pull=1/login_event=0`，成功返回 10 张卡片 |

点击事件的属性包含 `param`、`track_id`、`card_type`、`goto`、`page_from`、
`tm_card_play_state`、`rcmd_reason` 及卡片素材/关联字段等。字段存在不表示已证明每个字段的推荐权重，
本次仅记录名称，不在文档复制设备、账号、追踪或票据值。

各组还可读到 `tm.recommend.feed-card.0.show`、展示时长及播放器开始、暂停、恢复、结束事件。
在未安排点击的组也有播放器和历史记录；这些与首页自动播放相符，但尚未逐条关联到卡片，
不能把批次内所有播放都归给指定视频。日志请求发送时间也不等于每条事件生成时间。

首页参数在该批采集期间保持 `auto_refresh_state=1`、`inline_sound_cold_state=2`、
`autoplay_card=11`、`inline_sound=1`、`client_attr=0`、`fnval=17364`。
这些样本值与早先固定值方案有差异；尚未进行本轮设置切换或中国版对照，不能据此替换常量。

E 的原始文件名为 `between_batches.flows`：当时记录器未切换到独立 E 标签，
包含 D 之后的空闲区间。E 操作由用户确认，文件内其它事件不能全部归因于 E。
D 的 `progress` 是播放位置，`duration` 与视频长度相符，不能将二者当作本次累计有效观看时间。
本轮没有比较 NeoBili 真实流量，没有修改其生产实现，也没有验证这些上报对推荐结果的因果作用。

### 已有样本的追踪、会话与时间关联

继续离线读取同一批文件，解析了 56 条 Neuron 日志请求、87 条带播放器子消息的事件及
14 条移动观看心跳。此数字是消息数量，不是不同视频或完整协议覆盖率。
分帧与选定 Protobuf 解码未报错；未识别字段继续保留，不能据此宣称 schema 已完整验证。
脱敏关联结果保存为私有目录中的 `official_deep_analysis.json`。
字段名参照 8.89 静态描述符，9.13 国际版样本按实际字段号读取并做值关联。

**推荐来源传递**：七条推荐响应中，每批卡片的非空 `track_id` 只有一个值，
每批 9 或 10 张卡片共用它。因此该值在样本中是批次级关联，不能单独标识视频。
三个目标点击均通过 `param` 唯一匹配已返回卡片；其 `param/track_id/card_type/goto/title`
与对应卡片原值相等。GTA6 样本的 `rcmd_reason` 也与卡片相等；其余字段未一概判为复制。
三个目标起播事件的扩展 `track_id`、对应移动心跳的 `track_id` 也与推荐卡片相等。
已观测到推荐 → 点击 → 起播日志/移动心跳的同值关联，尚不能从网络样本指认内部赋值函数。

**播放器专用子消息**：播放事件除 extendedFields 外，还在外层字段 17 携带
视频及播放上下文；只解析 extendedFields 会漏掉 avid、progress、playerSessionId 等。
通过视频字段匹配后，C 中一条旧首页自动播放视频的结束事件与 GTA6 的起播事件可以分开，
不应把同一日志包里的所有播放器事件归给本次点击。
样本播放器 `progress` 的量级与毫秒位置相符：D 的两次结束为 17,793 与 150,648，
相应历史进度为 18 与 151 秒。这里只支持单位/取整关系相符，不凭三条记录确定完整舍入算法。

**会话关系**：D 第一次播放的开始、暂停、恢复、结束共用一个 playerSessionId；
退出后第二次点入形成另一值。两者在移动心跳中分别对应 `session`、`sessionID`，
这两个心跳字段彼此也相等。C/D 的目标播放器事件、点击及各组已读日志的 App sessionId
保持同一值，与播放 session 不同。仅限定本次前后台、暂停/恢复、退出重入样本，
不外推到登录切换、连续播放或播放器迁移。

**续播和计时**：D 第二次进入先报起播位置 0，随后出现自动 seek 事件与恢复位置 18,000，
说明此次自动续播到了约 18 秒。结束时心跳 `played_time=140`、`actual_played_time=140`、
`total_time=140`、`paused_time=0`，而 `last_play_progress_time/max_play_progress_time=151`。
第一次结束为 `played_time=18`、`actual_played_time=18`、`paused_time=4`、`total_time=22`。
因此播放位置、播放状态下的计时、暂停计时与视频长度是分别上报的量，不能互相替代。
与静态心跳计时路径的墙钟累加描述相符；第二段报告计时与位置增量也不完全相等，
缓冲状态、倍率变化及逐段取整的全部细节仍待受控操作，不以字段名称宣称实际有效观看已核实。

**服务器回执接续**：D 两段各自的起播移动心跳都带 `start_ts=0`，响应 `/data/ts`
返回该段时间值，随后结束请求的 `start_ts` 与该响应值一致。不同播放会话分别采用不同值，
这支持本次响应时间被后续请求采用，与静态 callback 写回路径相符；不外推为全局校时，
也未验证并发回执、失败或重试时的匹配行为。

**发送时点**：三条目标点击经 `/log/pbmobile/unrealtime` 发送，payload 的
`uploadTime-ctime` 分别约 3.513、9.292、2.016 秒；部分请求同时装有点击、起播、
播放器操作等多条事件。起播、暂停和结束也可批量延迟发送，因此不能仅按网络发送顺序
恢复用户动作顺序，应联合 ctime、播放 session 和视频关联。
目标 B 卡片两条展示时长事件经 realtime 发送，记录的时间窗约 93.121 与 11.851 秒；
第一条包含此前停留，不能把它们直接称作两段预定 10 秒操作。
realtime 路径本身也不意味着零延迟，未确认完整调度规则、阈值、失败重试及后台持久化。

后续官方行为研究优先补以下缺口：暂停/恢复、拖动/倍速/缓冲的计时变化；历史/搜索入口
与首页追踪来源区别；日志延迟与跨批发送；会话在连续播放、前后台及迁移时的复用规则。
中国版与国际版仍分开取证。本阶段不安排 NeoBili 对照、修改或推荐效果验收。
